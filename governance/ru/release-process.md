# Процесс выпуска

*Copyright © 2025 Ralph Gonzalez – https://olamip.org*

Этот документ определяет стандартный процесс, который я использую для создания, тестирования и публикации релизов спецификации OLAMIP и связанных инструментов. На данный момент все релизы управляются и принадлежат мне.

## 1. Версионирование

Я следую [Semantic Versioning 2.0.0](https://semver.org/):

- **MAJOR** версия при несовместимых изменениях формата или протокола.
- **MINOR** версия при добавлении новой функциональности или секций совместимо с предыдущими версиями.
- **PATCH** версия при исправлении ошибок, корректировке формулировок или уточнении правил без изменения поведения.

Пример: `1.0.0` → `1.0.1` (patch), `1.1.0` (minor), `2.0.0` (major).

## 2. Модель ветвления

Я использую простой Git-воркфлоу:

- `main` — стабильная ветка, всегда готовая к релизу.
- Ветки для фич или исправлений (например, `spec/delta-formats`, `fix/tag-rules`) — короткоживущие ветки для изменений.
- Ветки релиза (например, `release/v1.1.0`) — создаются непосредственно перед публикацией релиза.

## 3. Предварительные условия для релиза

Перед началом релиза я убеждаюсь, что:

- Все изменения, запланированные для этого релиза, слиты в `main`.
- Все автоматизированные проверки (линтинг, валидация схемы, скрипты сборки) проходят.
- Все issues и заметки, относящиеся к этому релизу, закрыты или задокументированы.
- `CHANGELOG.md` обновлён с чёткими, читаемыми для человека записями для этой версии.
- Документация актуальна, включая:
  - `file-format-specification.md`
  - `olamip-delta-file-format-specification.md`
  - `docs/introduction.md`
  - `faq.md`
- Примерочные файлы `olamip.json` и `olamip-delta.json` по-прежнему проходят валидацию по последним правилам.

## 4. Создание кандидата релиза

1. Создать ветку релиза из `main`:

   ```bash
   git checkout main
   git checkout -b release/vX.Y.Z
   ```

2. Обновить номера версий (если используются в инструментах, скриптах или помеченных активах, а не только в тексте спецификации).
3. Обновить `CHANGELOG.md` с заголовком релиза и заметками для этой версии.
4. Зафиксировать изменения:

   ```bash
   git add .
   git commit -m "chore(release): подготовка v1.1.0"
   ```

5. Отправить ветку:

   ```bash
   git push origin release/vX.Y.Z
   ```

6. Повторно запустить локальную или CI-валидацию и убедиться, что всё проходит.

## 5. Тестирование кандидата релиза

Поскольку релизами управляет только один человек, моё личное тестирование — основной контрольный пункт:

- Я проверяю, что примерочные файлы `olamip.json` и `olamip-delta.json` по-прежнему соответствуют схеме.
- Я убеждаюсь, что все примеры в двух файлах спецификации соответствуют описанным правилам.
- Я перечитываю обновлённые секции в спецификации и документации, чтобы выявить несоответствия.

Если нахожу серьёзные проблемы:

- Исправляю их в ветке `release`.
- Обновляю `CHANGELOG.md` и коммичу снова.
- Повторно провожу валидацию перед продолжением.

## 6. Финализация релиза

Когда кандидат стабилен:

1. Помечаю релиз в Git:

   ```bash
   git tag -a vX.Y.Z -m "Релиз v1.1.0"
   git push origin vX.Y.Z
   ```

2. Создаю релиз в GitHub (или эквивалент):

   - Использую тег `vX.Y.Z`.
   - Вставляю соответствующую секцию из `CHANGELOG.md` в описание релиза.
   - Прикрепляю сгенерированные артефакты (например, файлы схем, CLI-инструменты, tarball'ы снапшотов), если применимо.

## 7. Шаги после релиза

После публикации релиза:

- Обновляю внутренние заметки или дорожную карту о том, что было выпущено.
- Переношу отложенные элементы в бэклог или заметки для следующего релиза.
- Если есть канал связи (например, Twitter, рассылка, GitHub Discussions), опционально анонсирую новую версию и выделяю изменения.

## 8. Управление и надзор

Даже с одним мейнтейнером я поддерживаю слой управления:

- Любое изменение, затрагивающее основную схему, обязательные поля или версию протокола, должно быть чётко задокументировано в changelog.
- Значительные изменения самого процесса релиза (например, переход на новую схему версионирования или модель ветвления) должны быть задокументированы в краткой заметке управления или записи решения в `governance/decision-records/`.

## 9. Откат или патчи

Если релиз содержит критическую ошибку:

- Создаю патч-релиз как можно скорее (например, `v1.1.1`).
- Чётко документирую исправление в `CHANGELOG.md`.
- При необходимости обновляю документацию или каналы связи, отмечая, что предыдущая версия устарела или не рекомендуется.

## 10. Автоматизация и масштабирование

По возможности автоматизирую:

- Повторяющиеся шаги, такие как:
  - Проверка валидности JSON.
  - Валидация примерочных файлов по схеме.
  - Генерация или линтинг текста в стиле changelog.
- Держу процесс релиза простым, чтобы при присоединении контрибьюторов в будущем можно было передать или разделить те же шаги.

Этот процесс релиза принадлежит мне и поддерживается мной. Он может обновляться через обычный воркфлоу при улучшении самого процесса.
