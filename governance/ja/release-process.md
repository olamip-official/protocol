# リリースプロセス

*Copyright © 2025 Ralph Gonzalez – https://olamip.org*

このドキュメントは、OLAMIP 仕様および関連ツールのリリース作成、テスト、公開に私が使用する標準プロセスを定義します。現在、全てのリリースは私によって管理・所有されています。

## 1. バージョン管理

私は [Semantic Versioning 2.0.0](https://semver.org/) を使用します：

- **MAJOR** バージョン：フォーマットまたはプロトコルに非互換な変更を加えた場合
- **MINOR** バージョン：後方互換性を保ちつつ新機能やセクションを追加した場合
- **PATCH** バージョン：バグ修正、文言修正、動作変更なしのルール明確化の場合

例：`1.0.0` → `1.0.1` (patch)、`1.1.0` (minor)、`2.0.0` (major)。

## 2. 分岐モデル

シンプルな Git ワークフローを使用します：

- `main` — 安定ブランチ、常にリリース準備完了状態
- 機能または修正ブランチ（例：`spec/delta-formats`、`fix/tag-rules`）— 短命な変更ブランチ
- リリースブランチ（例：`release/v1.1.0`）— リリース直前に作成

## 3. リリースの前提条件

リリース開始前に確認します：

- 本リリース予定の全変更が `main` にマージ済み
- 全自動チェック（linting、スキーマ検証、ビルドスクリプト）がパス
- 本リリースに属する全 issue とメモがクローズまたはドキュメント化済み
- `CHANGELOG.md` が本バージョンの明確で読みやすいエントリで更新済み
- ドキュメントが最新、以下を含む：
  - `file-format-specification.md`
  - `olamip-delta-file-format-specification.md`
  - `docs/introduction.md`
  - `faq.md`
- サンプル `olamip.json`、`olamip-delta.json` が最新ルールで検証通過

## 4. リリース候補の作成

1. `main` からリリースブランチを作成：

   ```bash
   git checkout main
   git checkout -b release/vX.Y.Z
   ```

2. バージョン番号を更新（ツール、スクリプト、タグ付きアセットで使用されている場合、仕様テキストのみではない）
3. `CHANGELOG.md` を更新し、リリースヘッダーと本バージョンノートを追加
4. 変更をコミット：

   ```bash
   git add .
   git commit -m "chore(release): v1.1.0準備"
   ```

5. ブランチをプッシュ：

   ```bash
   git push origin release/vX.Y.Z
   ```

6. ローカルまたはCI検証を再度実行し、全てパスすることを確認

## 5. リリース候補のテスト

リリース管理者が1人であるため、私の個人テストが主要なゲートとなります：

- サンプル `olamip.json`、`olamip-delta.json` がスキーマに準拠することを検証
- 2つの仕様ファイルの全例が記述ルールと一致することを確認
- 仕様とドキュメントの更新セクションを読み、不整合を検出

重大な問題が見つかった場合：

- `release` ブランチで修正
- `CHANGELOG.md` を更新し再コミット
- 続行前に再検証

## 6. リリースの最終化

候補が安定したら：

1. Git でリリースをタグ付け：

   ```bash
   git tag -a vX.Y.Z -m "リリース v1.1.0"
   git push origin vX.Y.Z
   ```

2. GitHub リポジトリでリリース作成（または同等）：

   - タグ `vX.Y.Z` を使用
   - `CHANGELOG.md` の関連セクションをリリース説明に貼り付け
   - 該当する場合生成アーティファクト（スキーマファイル、CLIツール、スナップショット tarball）を添付

## 7. リリース後ステップ

リリース公開後：

- 出荷内容に関する内部メモまたはロードマップを更新
- 延期項目を次のリリース用バックログまたはメモに移動
- アウトリーチチャネル（Twitter、ニュースレター、GitHub Discussions）があれば、新バージョンを告知し変更点を強調（オプション）

## 8. ガバナンスと監督

単独メンテナでもガバナンス層を維持：

- コアスキーマ、必須フィールド、プロトコルバージョンに影響する変更は changelog で明確に文書化
- リリースプロセスの大幅変更（新バージョン管理スキームや分岐モデルへの移行など）は、`governance/decision-records/` に短いガバナンスノートまたは決定記録として文書化

## 9. ロールバックまたはパッチ

リリースに重大なバグが含まれていた場合：

- 可能な限り早くパッチリリースを作成（例：`v1.1.1`）
- `CHANGELOG.md` に修正を明確に文書化
- 必要に応じ前バージョンを非推奨または使用不推奨としてドキュメントまたは通信チャネルを更新

## 10. 自動化と将来のスケーラビリティ

可能な限り自動化：

- 繰り返し作業：
  - JSON 有効性チェック
  - スキーマに対するサンプルファイル検証
  - changelog 形式テキスト生成/リンティング
- コントリビューターが後で参加した場合に引き継ぎ・共有可能なようリリースプロセスをシンプルに維持

このリリースプロセスは私に帰属し、私が維持します。プロセス自体を改善する際は通常のワークフローを通じて更新可能です。
