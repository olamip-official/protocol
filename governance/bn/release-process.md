# রিলিজ প্রক্রিয়া (Release Process)

*কপিরাইট © ২০২৫ রালফ গনজালেজ – https://olamip.org*

এই নথিটি OLAMIP স্পেসিফিকেশন এবং সংশ্লিষ্ট টুলিং-এর রিলিজ তৈরি, পরীক্ষা এবং প্রকাশ করার জন্য আমি যে মানক প্রক্রিয়া ব্যবহার করি তা সংজ্ঞায়িত করে। বর্তমানে, সমস্ত রিলিজ আমার দ্বারাই পরিচালিত এবং রক্ষণাবেক্ষিত হয়।

---

## 1. ভার্সনিং

আমি [Semantic Versioning 2.0.0](https://semver.org/) অনুসরণ করি:

- **MAJOR** ভার্সন — যখন ফরম্যাট বা প্রোটোকলে অসামঞ্জস্যপূর্ণ পরিবর্তন করি  
- **MINOR** ভার্সন — যখন নতুন ফিচার বা সেকশন যোগ করি, কিন্তু ব্যাকওয়ার্ড‑কম্প্যাটিবল থাকে  
- **PATCH** ভার্সন — যখন বাগ ঠিক করি, শব্দচয়ন সংশোধন করি, বা নিয়ম পরিষ্কার করি কিন্তু আচরণ পরিবর্তন করি না  

উদাহরণ: `1.0.0` → `1.0.1` (patch), `1.1.0` (minor), `2.0.0` (major)

---

## 2. ব্রাঞ্চিং মডেল

আমি একটি সহজ Git ওয়ার্কফ্লো ব্যবহার করি:

- `main` — স্থিতিশীল, সর্বদা রিলিজ‑রেডি ব্রাঞ্চ  
- ফিচার বা ফিক্স ব্রাঞ্চ (যেমন `spec/delta-formats`, `fix/tag-rules`) — স্বল্পমেয়াদি পরিবর্তনের জন্য  
- রিলিজ ব্রাঞ্চ (যেমন `release/v1.1.0`) — রিলিজ প্রকাশের ঠিক আগে তৈরি করা হয়  

---

## 3. রিলিজের পূর্বশর্ত

রিলিজ শুরু করার আগে আমি নিশ্চিত করি:

- এই রিলিজের জন্য পরিকল্পিত সব পরিবর্তন `main`-এ মার্জ হয়েছে  
- সব স্বয়ংক্রিয় চেক (linting, schema validation, build scripts) পাস করেছে  
- এই রিলিজের অন্তর্ভুক্ত সব ইস্যু বা নোট বন্ধ বা নথিভুক্ত হয়েছে  
- `CHANGELOG.md` স্পষ্ট, মানব‑পাঠযোগ্য এন্ট্রি সহ আপডেট হয়েছে  
- ডকুমেন্টেশন আপডেট রয়েছে, যেমন:  
  - `file-format-specification.md`  
  - `olamip-delta-file-format-specification.md`  
  - `docs/introduction.md`  
  - `faq.md`  
- উদাহরণ `olamip.json` এবং `olamip-delta.json` ফাইলগুলো সর্বশেষ নিয়ম অনুযায়ী বৈধ  

---

## 4. রিলিজ ক্যান্ডিডেট তৈরি করা

1. `main` থেকে রিলিজ ব্রাঞ্চ তৈরি করুন:

   ```bash
   git checkout main
   git checkout -b release/vX.Y.Z
   ```

2. ভার্সন নম্বর আপডেট করুন (যদি টুলিং, স্ক্রিপ্ট বা ট্যাগড অ্যাসেটে ব্যবহৃত হয়)  
3. `CHANGELOG.md`-এ রিলিজ হেডার এবং নোট যোগ করুন  
4. পরিবর্তনগুলো কমিট করুন:

   ```bash
   git add .
   git commit -m "chore(release): prepare v1.1.0"
   ```

5. ব্রাঞ্চ পুশ করুন:

   ```bash
   git push origin release/vX.Y.Z
   ```

6. লোকাল বা CI ভ্যালিডেশন আবার চালান এবং নিশ্চিত করুন সবকিছু পাস করছে  

---

## 5. রিলিজ ক্যান্ডিডেট পরীক্ষা করা

কারণ রিলিজ একজন ব্যক্তির দ্বারা পরিচালিত হয়, আমার ব্যক্তিগত পরীক্ষা‑নিরীক্ষাই প্রধান গেট:

- উদাহরণ `olamip.json` এবং `olamip-delta.json` ফাইলগুলো স্কিমার সাথে সামঞ্জস্যপূর্ণ কিনা যাচাই করি  
- স্পেসিফিকেশন ফাইলের উদাহরণগুলো নিয়মের সাথে মেলে কিনা পরীক্ষা করি  
- আপডেট হওয়া সেকশনগুলো পড়ে অসঙ্গতি আছে কিনা দেখি  

যদি বড় সমস্যা পাই:

- `release` ব্রাঞ্চে ঠিক করি  
- `CHANGELOG.md` আপডেট করি  
- পুনরায় ভ্যালিডেশন চালাই  

---

## 6. রিলিজ চূড়ান্ত করা

ক্যান্ডিডেট স্থিতিশীল হলে:

1. Git-এ রিলিজ ট্যাগ করুন:

   ```bash
   git tag -a vX.Y.Z -m "Release v1.1.0"
   git push origin vX.Y.Z
   ```

2. GitHub রিলিজ তৈরি করুন:

   - ট্যাগ: `vX.Y.Z`  
   - `CHANGELOG.md` থেকে সংশ্লিষ্ট অংশ রিলিজ বর্ণনায় পেস্ট করুন  
   - প্রয়োজন হলে স্কিমা ফাইল, CLI টুল, বা স্ন্যাপশট টারবল সংযুক্ত করুন  

---

## 7. রিলিজ‑পরবর্তী ধাপ

রিলিজ প্রকাশের পরে:

- কী প্রকাশিত হয়েছে তা অভ্যন্তরীণ নোট বা রোডম্যাপে আপডেট করি  
- স্থগিত আইটেমগুলো পরবর্তী রিলিজের জন্য ব্যাকলগে সরাই  
- প্রয়োজনে সোশ্যাল বা কমিউনিটি চ্যানেলে ঘোষণা করি  

---

## 8. গভর্নেন্স এবং তদারকি

একজন মেইনটেইনার হলেও, আমি একটি গভর্নেন্স স্তর বজায় রাখি:

- স্কিমা, আবশ্যিক ফিল্ড বা প্রোটোকল ভার্সনে কোনো পরিবর্তন হলে তা স্পষ্টভাবে changelog-এ নথিভুক্ত করতে হবে  
- রিলিজ প্রক্রিয়ার বড় পরিবর্তন (যেমন নতুন ভার্সনিং স্কিম) `governance/decision-records/`-এ একটি সিদ্ধান্ত নোট হিসেবে সংরক্ষণ করতে হবে  

---

## 9. রোলব্যাক বা প্যাচিং

যদি কোনো রিলিজে গুরুতর বাগ থাকে:

- যত দ্রুত সম্ভব একটি প্যাচ রিলিজ করি (যেমন `v1.1.1`)  
- `CHANGELOG.md`-এ স্পষ্টভাবে নথিভুক্ত করি  
- প্রয়োজনে ডকুমেন্টেশন বা যোগাযোগ চ্যানেলে জানাই যে পূর্ববর্তী ভার্সন নিরুৎসাহিত  

---

## 10. অটোমেশন এবং ভবিষ্যৎ স্কেলিং

যেখানে সম্ভব, আমি অটোমেশন ব্যবহার করি:

- পুনরাবৃত্ত কাজ যেমন:  
  - JSON বৈধতা পরীক্ষা  
  - উদাহরণ ফাইল স্কিমার সাথে যাচাই  
  - changelog‑স্টাইল টেক্সট তৈরি বা লিন্ট করা  
- প্রক্রিয়াটি সহজ রাখি যাতে ভবিষ্যতে অবদানকারীরা যোগ দিলে একই ধাপ অনুসরণ করতে পারে  

এই রিলিজ প্রক্রিয়াটি আমার দ্বারা রক্ষণাবেক্ষিত এবং প্রয়োজন অনুযায়ী স্বাভাবিক ওয়ার্কফ্লো ব্যবহার করে আপডেট করা যেতে পারে।
