# عملية الإصدار (Release Process)

*حقوق النشر © 2025 رالف غونزاليس – https://olamip.org*

يشرح هذا المستند العملية القياسية التي أستخدمها لإنشاء واختبار ونشر إصدارات مواصفة OLAMIP والأدوات المرتبطة بها. في الوقت الحالي، تتم إدارة جميع الإصدارات من قبلي فقط.

---

## 1. إدارة الإصدارات (Versioning)

أتّبع قواعد **Semantic Versioning 2.0.0**: https://semver.org/

- **MAJOR** — عند إجراء تغييرات غير متوافقة مع الإصدارات السابقة.  
- **MINOR** — عند إضافة ميزات أو أقسام جديدة متوافقة مع الإصدارات السابقة.  
- **PATCH** — عند إصلاح الأخطاء أو تحسين الصياغة أو توضيح القواعد دون تغيير السلوك.  

مثال:  
`1.0.0` → `1.0.1` (تصحيح)، `1.1.0` (ثانوي)، `2.0.0` (رئيسي).

---

## 2. نموذج الفروع (Branching Model)

أستخدم سير عمل Git بسيطًا:

- `main` — الفرع المستقر الجاهز دائمًا للإصدار.  
- فروع الميزات أو الإصلاحات (مثل: `spec/delta-formats`، `fix/tag-rules`) — فروع قصيرة المدى للتغييرات.  
- فروع الإصدار (مثل: `release/v1.1.0`) — تُنشأ مباشرة قبل نشر الإصدار.  

---

## 3. المتطلبات قبل الإصدار

قبل بدء عملية الإصدار، أتأكد من:

- دمج جميع التغييرات المخطط لها في `main`.  
- نجاح جميع الفحوصات الآلية (linting، التحقق من المخطط، build scripts).  
- إغلاق أو توثيق جميع المشكلات والملاحظات المتعلقة بالإصدار.  
- تحديث `CHANGELOG.md` بملاحظات واضحة وسهلة القراءة.  
- تحديث الوثائق، بما في ذلك:  
  - `file-format-specification.md`  
  - `olamip-delta-file-format-specification.md`  
  - `docs/introduction.md`  
  - `faq.md`  
- استمرار توافق ملفات المثال `olamip.json` و`olamip-delta.json` مع أحدث القواعد.  

---

## 4. إنشاء إصدار مرشح (Release Candidate)

1. إنشاء فرع إصدار من `main`:

   ```bash
   git checkout main
   git checkout -b release/vX.Y.Z
   ```

2. تحديث أرقام الإصدارات (في الأدوات أو السكربتات أو الأصول إن وجدت).  
3. تحديث `CHANGELOG.md` بعنوان الإصدار وملاحظاته.  
4. تنفيذ commit:

   ```bash
   git add .
   git commit -m "chore(release): prepare v1.1.0"
   ```

5. رفع الفرع:

   ```bash
   git push origin release/vX.Y.Z
   ```

6. إعادة تشغيل الفحوصات المحلية أو CI والتأكد من نجاحها.  

---

## 5. اختبار إصدار المرشح

بما أنني المسؤول الوحيد عن الإصدارات، فإن الاختبار الشخصي هو المرحلة الأساسية:

- التحقق من أن ملفات المثال `olamip.json` و`olamip-delta.json` لا تزال متوافقة مع المخطط.  
- التأكد من أن جميع الأمثلة في مستندات المواصفة تتوافق مع القواعد الموضحة.  
- مراجعة الأقسام المحدثة لاكتشاف أي تناقضات.  

إذا ظهرت مشكلات كبيرة:

- أقوم بإصلاحها في فرع `release`.  
- تحديث `CHANGELOG.md` وإجراء commit جديد.  
- إعادة التحقق قبل المتابعة.  

---

## 6. إنهاء الإصدار

بعد استقرار إصدار المرشح:

1. وضع علامة الإصدار في Git:

   ```bash
   git tag -a vX.Y.Z -m "Release v1.1.0"
   git push origin vX.Y.Z
   ```

2. إنشاء إصدار على GitHub:

   - استخدام الوسم `vX.Y.Z`.  
   - نسخ القسم المناسب من `CHANGELOG.md` إلى وصف الإصدار.  
   - إرفاق أي ملفات ناتجة (مثل مخططات schema، أدوات CLI، أرشيفات snapshot) إن وجدت.  

---

## 7. ما بعد الإصدار

بعد نشر الإصدار:

- تحديث الملاحظات الداخلية أو خارطة الطريق بما تم إصداره.  
- نقل العناصر المؤجلة إلى قائمة المهام المستقبلية.  
- الإعلان عن الإصدار الجديد في حال وجود قناة تواصل (مثل Twitter أو GitHub Discussions).  

---

## 8. الحوكمة والإشراف

حتى مع وجود مسؤول واحد، أحافظ على طبقة حوكمة:

- يجب توثيق أي تغيير يؤثر على المخطط الأساسي أو الحقول المطلوبة أو إصدار البروتوكول بوضوح في changelog.  
- يجب توثيق التغييرات الكبيرة في عملية الإصدار ضمن سجل قرارات في `governance/decision-records/`.  

---

## 9. التراجع أو إصدار تصحيح (Patch)

إذا احتوى الإصدار على خطأ حرج:

- أقوم بإصدار تصحيح بأسرع وقت ممكن (مثل `v1.1.1`).  
- أوثّق الإصلاح بوضوح في `CHANGELOG.md`.  
- إذا لزم الأمر، أحدّث الوثائق أو أوضح أن الإصدار السابق غير موصى به.  

---

## 10. الأتمتة والتوسع المستقبلي

أقوم بأتمتة أكبر قدر ممكن:

- الخطوات المتكررة مثل:  
  - التحقق من صحة JSON  
  - التحقق من توافق ملفات المثال مع المخطط  
  - إنشاء أو تنسيق نص changelog  

أبقي العملية بسيطة بحيث يمكن مشاركتها بسهولة إذا انضم مساهمون جدد في المستقبل.

---

تتم إدارة عملية الإصدار هذه وصيانتها من قبلي، ويمكن تحديثها عبر سير العمل المعتاد كلما قمت بتحسينها.
