# रिलीज़ प्रक्रिया (Release Process)

*कॉपीराइट © 2025 राल्फ गोंजालेज़ – https://olamip.org*

यह दस्तावेज़ OLAMIP स्पेसिफिकेशन और संबंधित टूलिंग के रिलीज़ बनाने, परीक्षण करने और प्रकाशित करने के लिए मैं जो मानक प्रक्रिया उपयोग करता हूँ, उसे परिभाषित करता है। फिलहाल, सभी रिलीज़ मेरे द्वारा ही प्रबंधित और नियंत्रित किए जाते हैं।

---

## 1. वर्ज़निंग (Versioning)

मैं [Semantic Versioning 2.0.0](https://semver.org/) का पालन करता हूँ:

- **MAJOR** वर्ज़न — जब मैं फॉर्मेट या प्रोटोकॉल में असंगत (incompatible) बदलाव करता हूँ  
- **MINOR** वर्ज़न — जब मैं नई कार्यक्षमता या सेक्शन जोड़ता हूँ, लेकिन बैकवर्ड‑कम्पैटिबल रहता है  
- **PATCH** वर्ज़न — जब मैं बग ठीक करता हूँ, शब्दों को सुधारता हूँ, या नियम स्पष्ट करता हूँ बिना व्यवहार बदले  

उदाहरण: `1.0.0` → `1.0.1` (patch), `1.1.0` (minor), `2.0.0` (major)

---

## 2. ब्रांचिंग मॉडल (Branching Model)

मैं एक सरल Git वर्कफ़्लो उपयोग करता हूँ:

- `main` — स्थिर, हमेशा रिलीज़‑रेडी ब्रांच  
- फीचर या फिक्स ब्रांच (जैसे `spec/delta-formats`, `fix/tag-rules`) — अल्पकालिक बदलावों के लिए  
- रिलीज़ ब्रांच (जैसे `release/v1.1.0`) — रिलीज़ प्रकाशित करने से ठीक पहले बनाई जाती है  

---

## 3. रिलीज़ से पहले की आवश्यकताएँ

रिलीज़ शुरू करने से पहले मैं सुनिश्चित करता हूँ:

- इस रिलीज़ के लिए सभी बदलाव `main` में मर्ज हो चुके हैं  
- सभी स्वचालित जाँच (linting, schema validation, build scripts) पास हो चुकी हैं  
- इस रिलीज़ से संबंधित सभी इश्यू या नोट्स बंद या दस्तावेज़ित हैं  
- `CHANGELOG.md` इस वर्ज़न के लिए स्पष्ट, मानव‑पठनीय प्रविष्टियों के साथ अपडेट है  
- डाक्यूमेंटेशन अद्यतन है, जिसमें शामिल हैं:  
  - `file-format-specification.md`  
  - `olamip-delta-file-format-specification.md`  
  - `docs/introduction.md`  
  - `faq.md`  
- उदाहरण `olamip.json` और `olamip-delta.json` फाइलें नवीनतम नियमों के अनुसार वैध हैं  

---

## 4. रिलीज़ कैंडिडेट बनाना

1. `main` से रिलीज़ ब्रांच बनाएँ:

   ```bash
   git checkout main
   git checkout -b release/vX.Y.Z
   ```

2. वर्ज़न नंबर अपडेट करें (यदि टूलिंग, स्क्रिप्ट या टैग्ड एसेट में उपयोग होता है)  
3. `CHANGELOG.md` में इस रिलीज़ के लिए हेडर और नोट्स जोड़ें  
4. बदलाव कमिट करें:

   ```bash
   git add .
   git commit -m "chore(release): prepare v1.1.0"
   ```

5. ब्रांच पुश करें:

   ```bash
   git push origin release/vX.Y.Z
   ```

6. लोकल या CI वेलिडेशन फिर से चलाएँ और सुनिश्चित करें कि सब कुछ पास हो रहा है  

---

## 5. रिलीज़ कैंडिडेट का परीक्षण

क्योंकि रिलीज़ एक ही व्यक्ति द्वारा प्रबंधित है, मेरी व्यक्तिगत जाँच ही मुख्य गेट है:

- मैं उदाहरण `olamip.json` और `olamip-delta.json` फाइलों को स्कीमा के अनुसार सत्यापित करता हूँ  
- मैं सुनिश्चित करता हूँ कि स्पेसिफिकेशन फाइलों में दिए गए सभी उदाहरण नियमों से मेल खाते हों  
- मैं अपडेट किए गए सेक्शनों को पढ़कर किसी भी असंगति की जाँच करता हूँ  

यदि कोई महत्वपूर्ण समस्या मिलती है:

- मैं उसे `release` ब्रांच पर ठीक करता हूँ  
- `CHANGELOG.md` अपडेट करता हूँ  
- आगे बढ़ने से पहले पुनः वेलिडेशन करता हूँ  

---

## 6. रिलीज़ को अंतिम रूप देना

जब कैंडिडेट स्थिर हो जाए:

1. Git में रिलीज़ टैग करें:

   ```bash
   git tag -a vX.Y.Z -m "Release v1.1.0"
   git push origin vX.Y.Z
   ```

2. GitHub रिलीज़ बनाएँ:

   - टैग: `vX.Y.Z`  
   - `CHANGELOG.md` का संबंधित भाग विवरण में पेस्ट करें  
   - यदि आवश्यक हो, स्कीमा फाइलें, CLI टूल या स्नैपशॉट टारबॉल संलग्न करें  

---

## 7. रिलीज़ के बाद के चरण

रिलीज़ प्रकाशित होने के बाद:

- मैं आंतरिक नोट्स या रोडमैप अपडेट करता हूँ  
- स्थगित आइटमों को अगले रिलीज़ के बैकलॉग में ले जाता हूँ  
- यदि कोई आउटरीच चैनल है (जैसे Twitter, न्यूज़लेटर, GitHub Discussions), तो मैं वैकल्पिक रूप से घोषणा करता हूँ  

---

## 8. गवर्नेंस और निगरानी

एकल मेंटेनर होने के बावजूद, मैं एक गवर्नेंस लेयर बनाए रखता हूँ:

- स्कीमा, आवश्यक फ़ील्ड या प्रोटोकॉल वर्ज़न को प्रभावित करने वाले किसी भी बदलाव को changelog में स्पष्ट रूप से दस्तावेज़ित किया जाना चाहिए  
- रिलीज़ प्रक्रिया में किसी भी महत्वपूर्ण बदलाव (जैसे नया वर्ज़निंग मॉडल) को `governance/decision-records/` में एक निर्णय रिकॉर्ड के रूप में सहेजा जाना चाहिए  

---

## 9. रोलबैक या पैचिंग

यदि किसी रिलीज़ में गंभीर बग हो:

- मैं जल्द से जल्द एक पैच रिलीज़ बनाता हूँ (जैसे `v1.1.1`)  
- `CHANGELOG.md` में स्पष्ट रूप से दस्तावेज़ित करता हूँ  
- यदि आवश्यक हो, डाक्यूमेंटेशन या संचार चैनलों में नोट करता हूँ कि पिछला वर्ज़न अब अनुशंसित नहीं है  

---

## 10. स्वचालन और भविष्य का विस्तार

जहाँ संभव हो, मैं स्वचालन का उपयोग करता हूँ:

- दोहराए जाने वाले कार्य जैसे:  
  - JSON वैधता जाँच  
  - उदाहरण फाइलों को स्कीमा के विरुद्ध सत्यापित करना  
  - changelog‑शैली टेक्स्ट उत्पन्न या लिंट करना  
- मैं प्रक्रिया को सरल रखता हूँ ताकि भविष्य में योगदानकर्ता जुड़ें तो वे भी यही चरण आसानी से अपना सकें  

यह रिलीज़ प्रक्रिया मेरे द्वारा प्रबंधित है और आवश्यकता पड़ने पर सामान्य वर्कफ़्लो के माध्यम से अपडेट की जा सकती है।
