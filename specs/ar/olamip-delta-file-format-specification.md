# مواصفات تنسيق ملف OLAMIP-DELTA

*حقوق النشر © 2025 Ralph Gonzalez – https://olamip.org*

يعرّف بروتوكول **OLAMIP-DELTA** تنسيق ملف delta قائمًا على JSON للتحديثات التدريجية على `olamip.json`. هذه المواصفة مخصّصة لمديري المواقع والمطبّقين الذين لديهم معرفة مسبقة بالبيانات المهيكلة وHTML ونشر المحتوى بأسلوب شبيه بـ sitemap. 

## 1. نظرة عامة

يمثل `olamip.json` النسخة المرجعية الكاملة والموثوقة لبنية موقعك ومحتواه. أما `olamip-delta.json` فهو ملف مرافق اختياري يصف التغييرات التي حدثت منذ آخر تحديث. 

معًا، يشكلان تدفق تغييرات يمكن للآلة فهمه:

- `olamip.json`: لقطة كاملة ومهيكلة.
- `olamip-delta.json`: سجل تغييرات تدريجي.

---

## 2. المفاهيم الأساسية

- **Entry** — عنصر محتوى عند مستوى الورقة، مثل مقال مدونة أو صفحة منتج أو صفحة توثيق.
- **Section / Subsection** — تجميع هرمي، مثل فئة مدونة أو فئة توثيق أو مجموعة منتجات أو مجموعة مشاريع.
- **Operation** — إحدى القيم `added` أو `updated` أو `removed`.
- **Delta** — مجموعة تغييرات مرتبطة بتاريخ معيّن تتضمن `added` و`updated` و`removed`.

هذا التنسيق مصمم ليكون:

- **قابلًا للفهم الآلي أولًا**، مع بقائه مقروءًا بما يكفي للمراجعة اليدوية.
- **تدريجيًا**، بحيث تتمكن أنظمة الذكاء الاصطناعي من البقاء متزامنة دون إعادة معالجة الموقع بالكامل. 

---

## 3. موقع الملف وآلية الاكتشاف

### 3.1 موقع الملف

يجب استضافة `olamip.json` في جذر النطاق الخاص بك:

```text
https://yourdomain.com/olamip.json
```

ويجب استضافة `olamip-delta.json` في الدليل نفسه:

```text
https://yourdomain.com/olamip-delta.json
```

أما النسخ المؤرخة من delta، فهي اختيارية وتوجد في الدليل نفسه:

```text
/olamip.json
/olamip-delta-YYYY-MM-DD.json
```

### 3.2 آلية الاكتشاف

يجب على مديري المواقع الإعلان عن موقع `olamip.json` باستخدام الوسمين التاليين في `<head>` الخاص بالموقع:

```html
<link rel="olamip" href="https://yourdomain.com/olamip.json">
<meta name="olamip-location" content="https://yourdomain.com/olamip.json">
```

تتوقع أنظمة الذكاء الاصطناعي التي تعرف `olamip.json` العثور تلقائيًا على `olamip-delta.json` في الدليل نفسه وتطبيق التغييرات وفقًا لهذه المواصفة. لا حاجة لإضافة وسم `<link>` أو `<meta>` منفصل لـ `olamip-delta.json`.

## 4. البنية العليا

على المستوى الأعلى، يكون `olamip-delta.json` كائن JSON يحتوي على الحقول التالية:

```json
{
  "protocol": "OLAMIP-DELTA",
  "version": "1.0.0",
  "window_days": 7,
  "last_updated": "2026-04-28",
  "deltas": [
    {
      "date": "2026-04-27",
      "added": [
        {
          "title": "Example entry",
          "url": "https://example.com/page/",
          "summary": "...",
          "content_type": "blog_article"
        }
      ],
      "updated": [
        {
          "url": "https://example.com/page/",
          "summary": "Updated summary"
        }
      ],
      "removed": [
        {
          "url": "https://example.com/removed-page/"
        }
      ]
    }
  ]
}
```

### 4.1 الحقول العليا المطلوبة

- `protocol` (string، مطلوب)  
  يجب أن تكون القيمة `"OLAMIP-DELTA"`.  
  هذا يميّز ملف delta عن ملف OLAMIP الرئيسي وعن صيغ delta الأخرى.

- `version` (string، مطلوب)  
  يجب أن يطابق نظام الإصدارات الموثق، مثل `"1.0.0"`.  
  يتيح ذلك للمطوّرين اكتشاف تغييرات المخطط.

- `window_days` (integer، اختياري)  
  عدد الأيام في النافذة المتحركة؛ يجب أن يكون موجبًا، وعادة بين 7 و30.  
  يُطلب فقط عند استخدام ملف delta متحرك.

- `last_updated` (string، مطلوب)  
  تاريخ آخر تعديل لهذا الملف بصيغة ISO-8601 `YYYY-MM-DD`.  
  يساعد ذلك برامج الزحف على تحديد وقت إعادة الجلب.

- `deltas` (array، مطلوب)  
  مصفوفة غير فارغة من مجموعات التغييرات المرتبطة بالتاريخ.  
  كل عنصر فيها هو **كائن delta** يحتوي على `date` و`added` و`updated` و`removed`.

### 4.2 مصفوفة `deltas` وترتيب التواريخ

- يجب ترتيب `deltas` حسب `"date"` تصاعديًا، من الأقدم إلى الأحدث.
- يجب أن يحتوي كل كائن delta على الحقل `"date"` بصيغة ISO-8601 `YYYY-MM-DD`.
- يجب ألا تكون `deltas` فارغة.

هذا الترتيب ليس اختياريًا من حيث الامتثال؛ إذ تفترض أنظمة الذكاء الاصطناعي أن deltas مرتبة زمنيًا.

## 5. بنية كائن Delta

كل عنصر داخل `deltas` هو كائن delta بالشكل التالي:

```json
{
  "date": "2026-04-27",
  "added": [ ... ],
  "updated": [ ... ],
  "removed": [ ... ]
}
```

ولأجل الوضوح والقابلية للمعالجة الآلية، **يجب** على مديري المواقع تضمين حقول العمليات الثلاثة كلها في كل كائن delta، حتى لو كانت بعضُها مصفوفات فارغة.

الحقول:

- `date` (string) — تاريخ ISO-8601 بصيغة `YYYY-MM-DD`.
- `added` (array) — صفر أو أكثر من العناصر الجديدة.
- `updated` (array) — صفر أو أكثر من العناصر المعدّلة.
- `removed` (array) — صفر أو أكثر من العناصر المحذوفة.

مثال على كائن delta يصف الإضافات فقط:

```json
{
  "date": "2026-04-27",
  "added": [
    {
      "title": "New Page",
      "summary": "A new page added to the site.",
      "url": "https://example.com/new-page/"
    }
  ],
  "updated": [],
  "removed": []
}
```

هذا النمط مطلوب حتى عندما تنطبق عملية واحدة فقط في ذلك اليوم.

## 6. العمليات

### 6.1 `added`

العنصر داخل `added` هو **كائن كامل** من النوع المناسب (entry أو section أو subsection). يجب أن تتوافق الحقول مع مواصفة OLAMIP الخاصة بهذا النوع.

بالنسبة إلى **entry**:

- `title` (string، مطلوب) — عنوان قابل للقراءة البشرية.
- `summary` (string، مطلوب) — وصف موجز.
- `url` (string، مطلوب) — عنوان URL canonical مطلق.
- `content_type` (string، مطلوب) — من تصنيف `content_type` في OLAMIP.
- `tags` (array، اختياري) — قائمة tags بخاصية lowercase وعنصر واحد لكل token.
- `priority` (string، اختياري) — `"high"` أو `"medium"` أو `"low"`.
- `policy` (string، اختياري) — `"allow"` أو `"forbid"`.
- `language` (string، اختياري) — رمز لغة BCP-47.
- `metadata` (object، اختياري) — بيانات مهيكلة خاصة بالمجال.

بالنسبة إلى **section أو subsection**، تتبع الكائنات داخل `added` مواصفة section في OLAMIP، مع `title` و`summary` و`url` و`section_type` و`policy` و`tags` و`priority` وما إلى ذلك.

#### قواعد `added`

- يجب أن تتضمن عناصر `added` الحقل `url`.
- يجب أن تكون عناصر `added` كائنات كاملة، على الأقل تتضمن الحقول المطلوبة في مواصفة OLAMIP الرئيسية.
- لا يجوز أن يظهر أي `url` أكثر من مرة في كائن delta نفسه.

مثال:

```json
{
  "date": "2026-04-27",
  "added": [
    {
      "title": "مقالة مدونة جديدة",
      "summary": "مقدمة مختصرة عن الميزة الجديدة.",
      "url": "https://example.com/blog/new-feature/",
      "content_type": "blog_article",
      "tags": ["feature", "new"],
      "priority": "medium"
    }
  ],
  "updated": [],
  "removed": []
}
```

### 6.2 `updated`

يجب أن تتضمن عناصر `updated` الحقل `url`، ويمكن أن تكون:

- **كائنًا جزئيًا** يحتوي فقط على الحقول المتغيرة، أو
- **كائنًا كاملًا** يحتوي على جميع الحقول.

في أي عنصر `updated`، تُعتبر الحقول المفقودة **غير متغيرة**.

#### مثال على تحديث جزئي

```json
{
  "date": "2026-04-27",
  "updated": [
    {
      "url": "https://example.com/post/to-update/",
      "summary": "ملخص محدث مع معلومات جديدة.",
      "tags": ["feature", "update", "docs"]
    }
  ],
  "added": [],
  "removed": []
}
```

#### مثال على استبدال كامل

```json
{
  "date": "2026-04-27",
  "updated": [
    {
      "title": "عنوان المنشور المحدث",
      "summary": "ملخص محدث مع معلومات جديدة.",
      "url": "https://example.com/post/to-update/",
      "content_type": "blog_article",
      "tags": ["feature", "update", "docs"],
      "priority": "medium"
    }
  ],
  "added": [],
  "removed": []
}
```

#### قواعد `updated`

- يجب أن تتضمن عناصر `updated` الحقل `url`.
- يمكن أن تكون `updated` كائنًا جزئيًا أو كائنًا كاملًا.
- لا يجوز لـ `updated` تغيير هوية entry عبر إعادة تعيين `url`؛ فهذا قرار تكوين وليس شأنًا خاصًا بملف delta.

### 6.3 `removed`

العنصر داخل `removed` يجب أن يكون **أدنى حد ممكن** ويقتصر على الهوية.

```json
{
  "url": "https://example.com/page/to-remove/"
}
```

#### قواعد `removed`

- يجب أن تتضمن عناصر `removed` الحقل `url` فقط، ولا يجوز أن تتضمن أي حقول أخرى.
- يجب أن يكون `url` مطلقًا وcanonical.
- ينطبق `removed` على الـ URL المحدد وعلى أي عناصر فرعية هيكلية تحته (subsections وentries)، إن وجدت.
- لا يجوز أن يظهر أي `url` أكثر من مرة في كائن delta نفسه.

مثال:

```json
{
  "date": "2026-04-27",
  "removed": [
    {
      "url": "https://example.com/old-page/"
    }
  ],
  "added": [],
  "updated": []
}
```

## 7. الـ URL وهوية الكائن

يعتمد OLAMIP-DELTA على الـ URLs canonical كهوية رئيسية لـ entries وsections وsubsections.

### قواعد الهوية

- يجب أن يكون `url` عنوانًا مطلقًا يشمل البروتوكول والنطاق.
- لا يجوز أن يتكرر أي `url` أكثر من مرة داخل كائن delta نفسه، سواء في الإضافة أو التحديث أو الحذف.
- عند حذف section، تُعد جميع عناصره الفرعية محذوفة منطقيًا.
- تغيير URL يتطلب **remove** ثم **add**، وليس تحديثًا مباشرًا لـ `url`.

### أفضل الممارسات للـ URLs

- استخدم URLs canonical مستقرة ونادرًا ما تتغير.
- تجنب معلمات الاستعلام أو الأجزاء المرتبطة بجلسات مؤقتة.
- إذا انتقلت صفحة، فعاملها كمسألة redirect ومرجعية محتوى، لا كمسؤولية مباشرة داخل ملف delta.

## 8. نافذة Delta المتحركة (موصى بها)

تُعد **النافذة المتحركة** هي النمط الموصى به لـ `olamip-delta.json`.

في هذا النموذج:

- يحتوي ملف delta على التغييرات خلال آخر `window_days`.
- تقرأ أنظمة AI جميع deltas الموجودة في الملف وتطبقها بترتيب زمني.
- هذا يمنع فقدان التحديثات إذا تأخر الزاحف في الجلب. 

### مثال Delta متحرك (نافذة 7 أيام)

```json
{
  "protocol": "OLAMIP-DELTA",
  "version": "1.0.0",
  "window_days": 7,
  "last_updated": "2026-04-28",
  "deltas": [
    {
      "date": "2026-04-22",
      "added": [
        {
          "title": "منتج جديد A",
          "url": "https://example.com/product/a",
          "summary": "إضافة جديدة إلى الكتالوج."
        }
      ],
      "updated": [],
      "removed": []
    },
    {
      "date": "2026-04-23",
      "added": [],
      "updated": [
        {
          "url": "https://example.com/product/b",
          "summary": "تم تحديث الوصف ليعكس الميزات الجديدة."
        }
      ],
      "removed": []
    },
    {
      "date": "2026-04-24",
      "added": [],
      "updated": [],
      "removed": [
        {
          "url": "https://example.com/product/c"
        }
      ]
    }
  ]
}
```

تقوم أنظمة AI بما يلي:

- قراءة جميع deltas في الملف.
- تطبيقها بترتيبها الزمني.
- الوصول في النهاية إلى الحالة الأحدث.

## 9. Delta المؤرخة إصدارًا (بديل)

قد يفضل بعض مديري المواقع **delta مؤرخة**، حيث يحتوي كل ملف على تغييرات ليوم واحد.

### مثال على التخطيط

```text
/olamip.json
/olamip-delta-2026-03-01.json
/olamip-delta-2026-03-02.json
/olamip-delta-2026-03-03.json
```

### شكل الملف

يحتوي كل ملف إصدار على البنية المنطقية نفسها للملف المتحرك، لكنه يمثل تاريخ تغيير واحدًا فقط:

```json
{
  "protocol": "OLAMIP-DELTA",
  "version": "1.0.0",
  "date": "2026-03-02",
  "added": [
    {
      "title": "مقالة مدونة جديدة",
      "url": "https://example.com/blog/new-post/",
      "summary": "نظرة عامة قصيرة على التحديث."
    }
  ],
  "updated": [],
  "removed": []
}
```

### قواعد الاستيعاب

يجب على أنظمة AI:

- اكتشاف جميع الملفات `olamip-delta-*.json` في الدليل نفسه الذي يوجد فيه `olamip.json`.
- ترتيبها حسب `date` تصاعديًا.
- تطبيق فقط الملفات الواقعة ضمن النافذة المهيأة، مثل آخر 7–30 يومًا.

هذا النهج مفيد بشكل خاص لـ:

- المواقع الإخبارية ذات التحديثات اليومية المتكررة.
- كتالوجات التجارة الإلكترونية ذات الحجم الكبير.
- منصات التوثيق ذات دورات الإصدارات السريعة.

## 10. التغييرات الهيكلية: Sections وSubsections

يطبّق OLAMIP-DELTA نمط delta نفسه على **sections** و**subsections** كما يطبّقه على **entries**. وهذا يضمن أن تفهم أنظمة AI ليس فقط الصفحات الموجودة، بل أيضًا كيفية تنظيمها.

### 10.1 إضافة Section أو Subsection

عند إضافة section أو subsection، أدرج كائن **section كامل** داخل `added`.

مثال:

```json
{
  "date": "2026-05-01",
  "added": [
    {
      "title": "الدروس التعليمية",
      "summary": "أدلة خطوة بخطوة للمبتدئين والمستخدمين المتقدمين.",
      "url": "https://example.com/tutorials/",
      "section_type": "blog_category",
      "policy": "allow",
      "tags": ["tutorials", "beginner", "advanced"],
      "priority": "medium"
    }
  ],
  "updated": [],
  "removed": []
}
```

#### القواعد

- يجب أن تتضمن كائنات `added` الخاصة بالـ section الحقول `title` و`summary` و`url` و`section_type`.
- استخدم `section_type` ليعكس الدور الدلالي، مثل `blog_category` أو `doc_category` أو `product_collection` أو `research_category`.
- تساعد `priority` و`policy` أنظمة AI على فهم الأهمية وقواعد الاستيعاب للشجرة الفرعية بأكملها.

### 10.2 تحديث Section أو Subsection

أدرج `url` وأي حقول تغيرت.

مثال:

```json
{
  "date": "2026-05-02",
  "updated": [
    {
      "url": "https://example.com/blog/tutorials/",
      "title": "الدروس خطوة بخطوة",
      "summary": "أدلة للمبتدئين والمستخدمين المتقدمين، مع أمثلة برمجية وأفضل الممارسات.",
      "tags": ["tutorials", "beginner", "advanced", "code-examples"]
    }
  ],
  "added": [],
  "removed": []
}
```

#### القواعد

- يجب أن تتضمن الأقسام المحدثة `url`.
- يمكن أن يتضمن `updated` أي مجموعة فرعية من الحقول الأخرى.
- الحقول المفقودة تُعتبر غير متغيرة.

### 10.3 إزالة Section أو Subsection

أدرج فقط `url` داخل `removed`.

مثال:

```json
{
  "date": "2026-05-03",
  "removed": [
    {
      "url": "https://example.com/blog/retired/"
    }
  ],
  "added": [],
  "updated": []
}
```

#### القواعد

- يجب أن تتضمن عناصر `removed` الخاصة بالـ section الحقل `url` فقط، ولا يجوز إضافة أي حقول أخرى.
- يجب أن يكون الـ URL هو الـ canonical URL للقسم أو القسم الفرعي المحذوف.
- عند حذف section، تُعد جميع عناصره الفرعية محذوفة أيضًا.

## 11. الامتثال

ينبغي على المطبقين ومديري المواقع اعتبار ما يلي قواعد امتثال.

### 11.1 قواعد MUST

يجب أن يلتزم ملف OLAMIP-DELTA بما يلي:

- التصريح بـ `protocol: "OLAMIP-DELTA"`.
- ضبط `version` على قيمة تطابق نظام الإصدارات الموثق.
- تضمين مصفوفة `deltas` غير فارغة.
- أن يحتوي كل كائن delta على `date` بصيغة ISO-8601 `YYYY-MM-DD`.
- أن تُرتب `deltas` تصاعديًا حسب `date`.
- أن تتضمن كل دلتا الحقول الثلاثة (`added` و`updated` و`removed`) حتى لو كانت مصفوفات فارغة.
- أن يكون `url` في جميع العمليات عنوانًا مطلقًا وcanonical.
- عدم ظهور أي `url` أكثر من مرة داخل كائن delta نفسه.
- أن تتضمن `added` و`updated` الحقل `url`.
- أن يتضمن `removed` الحقل `url` فقط، دون أي حقول أخرى.
- اعتبار الحقول المفقودة في `updated` غير متغيرة.
- اعتبار `removed` بمثابة حذف للـ URL المحدد وجميع العناصر الفرعية تحته من الفهرس. 

### 11.2 قواعد SHOULD

ينبغي أن:

- يعتمد التنفيذ على **النافذة المتحركة** كخيار افتراضي، ما لم يكن سير العمل أنسب لـ delta المؤرخة.
- تبقى `last_updated` دقيقة لكي تعرف برامج الزحف والموثّقون متى أصبح الملف جديدًا.
- تُستخدم URLs canonical مستقرة ونادرًا ما تتغير لتجنب الغموض عند تطبيق delta.
- تبقى `window_days` عادة بين 7 و30 يومًا بحسب وتيرة النشر.
- في حالة delta المؤرخة، يجب الاحتفاظ بعدد كافٍ من الملفات داخل النافذة المحددة، مثل آخر 7–30 يومًا، حتى لا تضيع التحديثات إذا تأخر الزاحف.

### 11.3 قواعد MAY

يجوز للتنفيذ المتوافق أن:

- يستخدم صيغة delta المؤرخة (`olamip-delta-YYYY-MM-DD.json`) بدلًا من ملف متحرك واحد إذا كان ذلك أنسب لمسار النشر.
- ينشر `olamip-delta.json` بوتيرة أعلى أو أقل من `olamip.json` ما دام الرابط بين snapshot وdelta واضحًا ومتسقًا.
- يضيف بيانات تشخيصية أو سجلات تحت مفتاح منفصل خارج حقول البروتوكول، مثل كائن `diagnostics`، بشرط ألا يتعارض مع الحقول المطلوبة أو يغيّر معنى delta.

## 12. أفضل الممارسات

لضمان توافق قوي وطويل الأمد مع أنظمة AI، ينبغي على مديري المواقع اتباع أفضل الممارسات التالية عند توليد `olamip-delta.json`.

### 12.1 أتمتة توليد delta

- اربط توليد delta بنظام CMS أو مسار النشر لديك.
- كلما نُشر محتوى أو جرى تحديثه أو حذفه، حدّث `olamip-delta.json` وفقًا لذلك.
- تحقق من مخطط الملف قبل النشر لتجنب أخطاء البنية أو الحقول غير الصالحة.

### 12.2 اجعل `olamip.json` المصدر المرجعي

- حافظ على `olamip.json` صحيحًا ومحدّثًا.
- يمكن لأنظمة AI الجديدة أن تبدأ من الملف الكامل ثم تطبق deltas اللاحقة.
- لا تتعامل مع `olamip-delta.json` كبديل عن snapshot الرئيسي.

### 12.3 استخدم URLs canonical مستقرة

- استخدم URLs مطلقة مع البروتوكول والنطاق.
- تجنب أنماط URLs التي تتغير كثيرًا، إلا إذا كانت آلية الموقع، مثل redirects، قوية بما يكفي للحفاظ على المعنى canonical.
- إذا تغيّر URL صفحة تغييرًا حقيقيًا، فتعامل مع ذلك على أنه “remove-then-add” وليس تحديثًا مباشرًا لـ `url` داخل delta.

### 12.4 حافظ على اتساق الملخصات والبيانات الوصفية

- يجب أن تكون الملخصات في عناصر `added` و`updated` متسقة مع المحتوى الفعلي.
- التعديلات اللفظية الصغيرة التي لا تغيّر المعنى يمكن إرسالها كـ delta، لكن ينبغي تقليلها لتجنب churn غير الضروري.
- يجب أن تكون tags موحّدة، بحروف صغيرة، وكلمة واحدة، ومربوطة بشرطة إذا كانت متعددة الكلمات، وأن تعبّر عن مفاهيم مستقرة.

## 13. موارد ذات صلة

لفهم منظومة OLAMIP بشكل كامل، ينبغي على مديري المواقع أيضًا مراجعة:

- **[مواصفة تنسيق ملف OLAMIP](https://olamip.org/file-format-specification/)**  
  تشرح بنية `olamip.json` وتعرّف الحقول الخاصة بـ entries وsections وsubsections التي تقوم عليها صيغة delta.

- **[الأسئلة الشائعة حول OLAMIP](https://olamip.org/frequently-asked-questions/)**  
  تشرح أسئلة النشر والاكتشاف والتشغيل لمديري المواقع.

- **[مواصفة تنسيق ملف OLAMIP-DELTA](https://olamip.org/delta-updates/)**  
  مخطط JSON رسمي لـ `olamip-delta.json` يمكن استخدامه للتحقق الآلي وlinting لملفات delta.

- **[لماذا OLAMIP معيار متفوق على LLMs.txt](https://olamip.org/why-olamip-is-a-superior-standard-to-llms-txt/)**  
  يوضح مزايا OLAMIP وOLAMIP-DELTA مقارنة بصيغ البيانات الوصفية الأبسط وغير المهيكلة.
